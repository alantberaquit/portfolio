Learning objective

Make a reasoned selector choice — not a guess.

By the end of this module, you should be able to:

Compare possible target selectors and choose the option that is most stable, appropriately specific, and resilient to normal UI changes.

The goal is not to memorize one selector pattern. The goal is to develop the judgment to choose the strongest available target for the situation.

Selector decision hierarchy

Start with the most stable signal available.

The first selector that works is not automatically the best selector. Evaluate the element from strongest evidence to weaker fallbacks.

1

Stable unique ID

Use an element or container ID when it is unique and remains unchanged across refreshes, sessions, roles, and expected UI states.

#trandate_fs
2

Stable data-* attribute

Automation-oriented attributes are often strong because they describe application intent instead of visual position.

[data-automation-id="save"]
3

Stable semantic attribute

Attributes such as name, href, aria-label, or another stable business-facing attribute can be good fallbacks.

input[name="trandate"]
4

Stable contextual targeting

When the child itself has no useful identifier, anchor the selector to a stable parent or section before targeting the child.

#billing-panel button.edit
5

Position only as a fallback

eq(), nth-child(), and deep DOM paths can work, but they depend on current structure and should be used carefully.

#item_headerrow td:eq(1)
6

Validate in context

A strong selector must remain unique and reliable after refresh, navigation, expansion panels, role changes, or other relevant state changes.

refresh → reopen → retest
Stable ID?→ Stable data-*?→ Stable semantic attr?→ Stable parent context?→ Positional fallback
Worked example 1 · Inspect the DOM

One field. Three selectors. Only one should be your first choice.

Imagine this simplified transaction form. Your guide needs to target the Date field.

Representative DOMsanitized example
<div id="main_form">
  <div class="field-row">
    <label for="trandate">Date</label>

    <input
      id="trandate_fs"
      name="trandate"
      type="text"
      class="inputreq"
    />
  </div>
</div>

Candidate selectors

#trandate_fsPreferred

Direct, unique, and independent of the field's current page position.

input[name="trandate"]Good fallback

Also meaningful if the name is stable and unique. Useful when the ID is unavailable or unstable.

#main_form div:nth-child(4) inputFragile

Works only while that field remains in the same structural position.

Uniqueness

The selector should identify one intended target, not several similar fields.

Stability

The attribute should remain predictable after refresh, navigation, and normal application changes.

Minimal dependence

Avoid depending on parent depth or sibling position when a direct stable identifier already exists.

Worked example 2 · Automation attributes

When there is no trustworthy ID, look for purposeful attributes.

Here the button's CSS class looks generated, but the automation attribute communicates the actual application action.

Representative DOMbutton example
<div class="transaction-actions">
  <button
    class="oj-button oj-component-9381"
    data-automation-id="EDIT_TRAN_JOURNAL"
    type="button"
  >
    Edit
  </button>
</div>

Compare the evidence

[data-automation-id="EDIT_TRAN_JOURNAL"]Strong

Purposeful and tied to the application's action semantics.

.oj-component-9381Risky

Looks generated. If the framework regenerates the class, the guide breaks.

button:contains("Edit")Lower priority

Visible text may change, be translated, or appear on multiple buttons.

Important judgment

A selector is not strong because it looks technical. It is strong because the underlying attribute is stable, unique, and meaningful in the application.

Deep dive · Dynamic attributes

An ID is only useful if it stays the same.

Developers often assume that every id is automatically the strongest selector. That is not always true.

Session 1same field
<input
  id="custfield_948271"
  name="custfield"
  data-field-key="customer_reference"
/>
Session 2after refresh/login
<input
  id="custfield_612450"
  name="custfield"
  data-field-key="customer_reference"
/>

Looks strong, but fails

#custfield_948271

The ID changed between sessions. A selector that was perfect yesterday no longer matches today.

Better candidate

[data-field-key="customer_reference"]

If this attribute is verified stable and unique, it is a stronger target than the dynamic ID.

Deep dive · Duplicate elements

Uniqueness can change when the UI state changes.

A selector may be unique when a page first loads, then become ambiguous after a panel opens, a template renders, or another matching control appears.

Expanded UI statetwo Edit buttons
<section data-record-id="A102">
  <button class="edit-btn">Edit</button>
</section>

<section data-record-id="B410">
  <button class="edit-btn">Edit</button>
</section>

Why the simple selector fails

.edit-btn2 matches

It does not identify which record's Edit button the guide needs.

[data-record-id="B410"] .edit-btnContextual

The stable parent provides the context needed to identify the correct child button.

Troubleshooting question

When a selector starts matching the wrong element, ask first: “Did the number of matches change in this UI state?”

Deep dive · Positional selectors

Position can be valid — but understand the tradeoff.

Sometimes a stable direct identifier simply does not exist. Positional targeting can be acceptable as a fallback, especially when anchored to a stable context.

Representative tablerole-dependent columns
<tr id="item_headerrow">
  <td>Item</td>
  <td>Account</td>
  <td>Amount</td>
</tr>

Possible approach

#item_headerrow td:eq(1)Conditional

Reasonable only if the column order is known to be stable in every relevant role/state.

#item_headerrow td[data-label="Account"]Better if available

A stable descriptive attribute survives column reordering better than index-based targeting.

Use position deliberately

Do not reject positional selectors automatically. Use them when stronger signals truly are unavailable.

Anchor when possible

Position inside a stable parent is safer than a global page position.

Test role/state changes

If layout can vary by role, center, or expanded state, validate those variants.

From the Guide Developer Library

Five questions before you lock in a selector.

Is it unique?Does it identify only the intended target?
Is it stable?Will the attribute persist across sessions and normal UI changes?
Is it meaningful?Does it describe the intended element rather than its current position?
Is it too brittle?Are you depending on deep DOM structure or generated classes?
Did you test it?Validate uniqueness and stability after refresh or state changes.

Decision shortcut

Prefer: stable ID → stable data-* → stable semantic attributes such as name/href → contextual/positional selectors only when stronger options are unavailable.
